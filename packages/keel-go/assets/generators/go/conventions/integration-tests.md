# Pruebas de integración de los escenarios `FL-*`

Cómo se traduce `specs/validation-scenarios.md` a código en `tests/integration/`. Es la convención del agente
`keel-go-tests` y la referencia de `keel-go-validate` cuando arbitra un fallo.

**Qué no es**: las pruebas unitarias que dejó build junto al código. Lo que hay aquí son escenarios end-to-end
contra el servidor real y la infraestructura de `infra/docker-compose.yaml`: el mismo trabajo que antes se hacía
con `curl` a mano, ahora versionado. Y son la traducción de los **mismos** escenarios que los servidores de
keel-spring, keel-nest y keel-dotnet del diseño ejecutan en JUnit, Vitest y xUnit: si uno pasa en un servidor y no
en otro, alguno no es equivalente.

## La caja negra

Las pruebas de flujo **no importan ningún paquete del servicio**: arrancan el servidor como un proceso aparte (el
mismo binario que se despliega) y le hablan HTTP y JSON. Dentro del módulo nada impide ese import, así que
`bash infra/check-flows.sh` lo comprueba: pregunta a `go list` qué importan las pruebas y sale en rojo si aparece
un paquete del módulo. Un flujo que nombre un DTO, un mensaje, un enum o un error del servicio no pasa ese gate.
Solo la biblioteca estándar, como el propio arnés.

## La restricción `integration`

Todo archivo de `tests/integration/` empieza por `//go:build integration` (y una línea en blanco antes de
`package integration`) y se llama `<algo>_test.go`. Así `go test ./...` y `go build ./...` no lo ven: estas pruebas
necesitan la infraestructura arriba. Una prueba de flujo sin la restricción la ejecutaría `go test ./...` sin base y
saldría en rojo por algo que no es suyo.

Los tuyos llevan la restricción y **no** la cabecera `// Code generated by keel-go. DO NOT EDIT.`: esa es la de los
archivos del arnés.

## El arnés

Lo genera build en el mismo paquete (`flow_test.go`, `harness_test.go`, `server_test.go`, `json_shape_test.go`,
`failure_capture_test.go`, `harness_smoke_test.go`) y **no se edita** (ver § El arnés es del generador).

| Pieza | Para qué |
|---|---|
| `f := StartFlow(t, given)` | prepara el flujo: arranca el servidor (una vez por suite, perfil `local`, en `127.0.0.1` y un puerto libre), **resetea el estado** (`infra/reset-db.sh`) y ejecuta `given`, el Given común a todo el flujo (puede ser `nil`); si algo de eso falla, los escenarios salen OMITIDOS |
| `f.Scenario("FL-…: …", func(s *Scenario) {…})` | un escenario: un subtest cuyo título es el nombre del caso en el XML; los de un flujo se ejecutan **en el orden en que están escritos** |
| `s.Get(ruta)`, `s.Post/Put/Patch(ruta, cuerpo)`, `s.Delete(ruta)` | una petición HTTP de verdad; nunca falla por un 4xx/5xx: el status es una aserción. El cuerpo es el JSON ya escrito (`string`), tal cual viaja, o un valor que se serializa |
| `s.Get(ruta, cabeceras...)` y los demás | las mismas, con cabeceras (`http.Header`) detrás: se juntan todas |
| `s.Exchange(método, ruta, cuerpo, cabeceras)` | cualquier verbo, con cabeceras (`http.Header`, o `nil`) |
| `s.ExchangeAll(Request{…}, Request{…})` | varias peticiones **a la vez**, con las respuestas en el orden pedido: la única forma de escribir un escenario de carrera |
| `got.Status`, `got.Header.Get(n)`, `got.Body` | el intercambio crudo (`*Response`) |
| `got.JSON()` | el cuerpo como JSON, con cada número como su **texto** (`json.Number`): `"2.50"` no es `"2.5"` |
| `s.ExpectStatus(got, 201)` | el status, con el cuerpo en el motivo si falla |
| `s.AssertJSON(esperado, got)` | el cuerpo entero contra el JSON esperado, **estricto** (ni una clave de más ni de menos, números por su texto, listas en orden), con los comodines `"<uuid>"`, `"<instant>"` y `"<any>"` para lo que genera el servidor |
| `RouteBase` | el prefijo de todas las rutas (basePath + versión) |
| `s.Db(sql)` | una sentencia contra la base de prueba (solo con persistencia): para lo que no se ve por HTTP |
| `s.ResetState()` | el reset, a mano (`StartFlow` ya lo hace al empezar cada flujo) |
| `s.Eventually(cond, plazo, mensaje)` | espera a que algo asíncrono se cumpla (plazo cero: 10 s) |
| `s.BaseURL()` | la URL del servidor arrancado, por si un escenario necesita construir una a mano |
| `s.Errorf`, `s.Fatalf`, `s.Error`, `s.Fatal` | las aserciones propias: marcan el escenario en rojo **y** apuntan el motivo en su evidencia |

Las aserciones van siempre por el `*Scenario` (`s`), nunca por el `t` del flujo: `s.Errorf` apunta el motivo en
`build/keel-failures/<id>.json`, que es lo que lee el árbitro; `t.Errorf` lo dejaría sin evidencia y en el flujo
equivocado. Un pánico dentro de un escenario se recupera como el FALLO de ese escenario y la suite sigue.

Una cabecera va en el último argumento de `Exchange`:

```go
got := s.Exchange(http.MethodPost, RouteBase+"/products", body, http.Header{"Idempotency-Key": {key}})
```

Y dos peticiones **a la vez** van por `ExchangeAll`, nunca con goroutines propias: un `Fatal` desde la goroutine de
una petición no para el escenario, y un pánico ahí tumba la suite entera con el servidor vivo.

```go
both := s.ExchangeAll(
	Request{Method: http.MethodPost, Path: RouteBase + "/products", Body: body, Headers: http.Header{"Idempotency-Key": {key}}},
	Request{Method: http.MethodPost, Path: RouteBase + "/products", Body: body, Headers: http.Header{"Idempotency-Key": {key}}},
)
```

## Las credenciales

Con capa `security`, el arnés trae `tests/integration/credentials_test.go`, con lo que siembra el proveedor de
identidad de prueba (`infra/test-credentials.env`, del mismo productor que el realm). Cada función existe solo si
el diseño la hace posible:

| Pieza | Cuándo existe | Para qué |
|---|---|---|
| `Bearer(token)` | siempre que hay tokens | la cabecera `Authorization`: `s.Get(ruta, Bearer(s.TokenFor("rol")))` |
| `s.TokenFor(rol)` | con roles | el usuario de prueba del rol; `s.TokenFor("no-role")` es el autenticado sin roles (el 403) |
| `s.SecondTokenFor(rol)` | con roles | el SEGUNDO usuario del rol: otro titular con los mismos permisos |
| `s.ServiceCredential(cliente)` | con `serviceAuth` | el token de máquina de un cliente del diseño o de la matriz `test-m2m-*` |
| `s.TokenAs(Persona{…})` | identidad del llamante en un claim, con Keycloak | una persona con el `sub` exacto y los claims del escenario |

Se llaman **en cada petición** y no se guarda lo que devuelven: el token dura cinco minutos y se renueva solo si se
le pregunta. Si el proveedor no lo da, el escenario termina ahí con el motivo (no hace falta comprobar el error).

```go
got := s.Post(RouteBase+"/me/card", body, Bearer(s.TokenFor("card-holder")))
other := s.Get(RouteBase+"/me/card", Bearer(s.SecondTokenFor("card-holder")))
ana := Bearer(s.TokenAs(Persona{Sub: "sub-ana-001", Claims: map[string]string{"email": "ana@x.test"}}))
noEmail := Bearer(s.TokenAs(Persona{Sub: "sub-ana-001", Without: []string{"email"}}))
both := s.Get(RouteBase+"/me/card", ana, http.Header{"X-Correlation-Id": {"c-1"}})
```

`Persona.Without` es «el mismo token sin ese claim»; `Persona.Role`, el rol de realm de la persona (vacío, ninguno).
Un `sub` va en `Persona.Sub`, nunca entre los claims.

## La mensajería

Con capa `messaging`, el arnés trae `tests/integration/messaging_test.go`: el broker se maneja desde el escenario por
el contenedor devtools de `infra/`, y `StartFlow` espera, al abrir cada flujo, a que el broker esté arriba y el servidor
conectado a él (SMOKE-8 lo comprueba en el humo).

| Pieza | Cuándo existe | Para qué |
|---|---|---|
| `s.Deliver<Suscripción>(messageID, payloadJSON)` | por suscripción | entrega un mensaje de esa suscripción en su canal real, con la envoltura de su contrato; el MISMO `messageID` dos veces es la reentrega que el consumidor tiene que absorber |
| `s.DeliverMessage(canal, clave, cuerpo, cabeceras)` | siempre | un mensaje crudo en un canal (un evento ajeno del canal compartido, un cuerpo roto); con RabbitMQ falla si el broker no lo enrutó, con Kafka la clave es la del registro, y con SNS/SQS se publica en el topic con las cabeceras como message attributes (sin `eventType`, el filtro de la suscripción lo deja fuera) y la clave no viaja. `cabeceras` puede ser `nil` |
| `s.PublishedMessages(canal)` | siempre | lo publicado en un canal del diseño desde el reset (`[]BrokerMessage` con `RoutingKey`, `Properties`, `Body`, y `Payload()`, `EventID()`, `EventType()`, `Type()`); con outbox, espera antes a que el relay entregue lo pendiente. Leer no consume |
| `s.DeadLetterMessages(suscripción)` | siempre | lo que acabó en el descarte de una suscripción: úsalo también para la aserción NEGATIVA (el duplicado absorbido no acaba aquí) |
| `s.PurgeMessages(canal o suscripción)` | siempre | vacía un canal justo antes de la acción cuyo Then afirma que NO se publica nada (con Kafka, que no borra, mueve la marca de lectura al final; con SNS/SQS, lo publicado se lee y se purga en la cola de arnés de cada canal) |
| `s.StopBroker()` / `s.StartBroker()` | siempre | el canal indisponible: lo para, y lo levanta esperando a que el servidor vuelva a estar conectado |
| `s.DeadLetteredEvents()` | con `reliability: outbox` | cuántos eventos se rindió el outbox: el Then natural de casi cualquier escenario del outbox es que siga en 0 |
| `s.AbandonOutboxEvent(evento)` / `s.ClearAbandonedOutboxEvents()` | con `reliability: outbox` | agota el presupuesto de reintentos del evento pendiente de ese tipo (la precondición de la rendición) y lo retira después |

Lo asíncrono se afirma con `s.Eventually`, nunca con una espera fija:

```go
s.ExpectStatus(s.Post(RouteBase+"/reservations", body), 201)
s.Eventually(func() bool {
	return slices.ContainsFunc(s.PublishedMessages("stockEvents"), func(m BrokerMessage) bool { return m.EventType() == "StockReservationRequested" })
}, 20*time.Second, "no se publicó la petición de reserva")
s.DeliverStockReserved(eventID, `{"orderId":"0190a1b2-c3d4-7e5f-8a9b-0c1d2e3f4a5b"}`)
```

Los métodos del escenario terminan el escenario si fallan, así que **no se llaman desde una goroutine**: dos entregas a
la vez se escriben con `s.ExchangeAll` si entran por HTTP, y si entran por el broker, una tras otra (el broker las
encola igual).

## Una función por flujo

```go
//go:build integration

package integration

import (
	"net/http"
	"strings"
	"testing"
)

// TestProductCreation es FL-PRD-001 · se da de alta un producto.
func TestProductCreation(t *testing.T) {
	f := StartFlow(t, nil)
	// El estado que encadena los escenarios del flujo: una variable de la función, que comparten los cierres.
	var productID string

	f.Scenario("FL-PRD-001: se da de alta un producto", func(s *Scenario) {
		body := `{"sku":"ACM-0001","name":"Martillo de carpintero","price":{"amount":12.50,"currency":"EUR"},"apiToken":"tok-123"}`
		got := s.Exchange(http.MethodPost, RouteBase+"/products", body, http.Header{"Idempotency-Key": {"7d4c1a0e-5b8f-4a52-9a0e-1f0a6c1f2b01"}})
		s.ExpectStatus(got, http.StatusCreated)
		s.AssertJSON(`{"id":"<uuid>","sku":"ACM-0001","name":"Martillo de carpintero","notes":null,"price":{"amount":12.50,"currency":"EUR"},"status":"draft"}`, got)
		productID = stringField(s, got, "id")
		if location := got.Header.Get("Location"); !strings.HasSuffix(location, "/api/v1/products/"+productID) {
			s.Errorf("Location = %q, quiero que termine en /api/v1/products/%s", location, productID)
		}
	})

	f.Scenario("FL-PRD-001-C: un sku que ya existe se rechaza", func(s *Scenario) {
		body := `{"sku":"ACM-0001","name":"Otro martillo","price":{"amount":9.99,"currency":"EUR"}}`
		got := s.Exchange(http.MethodPost, RouteBase+"/products", body, http.Header{"Idempotency-Key": {"0b9e2f6a-3c1d-4e7b-8a5f-2d6c9e1a4b02"}})
		s.ExpectStatus(got, http.StatusConflict)
		if code := stringField(s, got, "code"); code != "SKU_ALREADY_EXISTS" {
			s.Errorf("code = %q, quiero SKU_ALREADY_EXISTS", code)
		}
	})
}

// stringField es el campo name de un cuerpo JSON objeto, o el escenario termina diciendo por qué no está.
func stringField(s *Scenario, got *Response, name string) string {
	s.Helper()
	value, err := got.JSON()
	if err != nil {
		s.Fatal(err)
	}
	object, _ := value.(map[string]any)
	text, ok := object[name].(string)
	if !ok {
		s.Fatalf("el cuerpo no trae %q como texto: %s", name, got.Body)
	}
	return text
}
```

Reglas de forma:

- **Una función `Test<Flujo>` por flujo**, en `tests/integration/<flujo>_test.go`, con el id del flujo en su
  comentario. Un subtest por flujo partiría la matriz: el escenario es el subtest.
- **El título de cada escenario empieza por su id y dos puntos** (`f.Scenario("FL-PRD-001-C: …", …)`). De ahí
  salen la matriz de `score-scenarios.sh` y el nombre del volcado de su evidencia. Sin el id, el escenario sale
  `NO_EJERC` aunque se ejecute. El primer escenario de un flujo suele llevar el id del flujo a secas
  (`FL-PRD-001`), como el documento.
- **Un caso borde va DENTRO del escenario que lo declara** (la lista **Casos borde** de su bloque), como una
  aserción más de ese mismo `f.Scenario`. Nunca con un id que el documento no declara (un `FL-PRD-001-G` para el
  borde de `FL-PRD-001-F`): la matriz contaría un escenario que el diseño no tiene, y `score-scenarios.sh` lo
  puntuaría igual, porque cuelga de un flujo declarado.
- **El reset es por flujo, no entre escenarios**: dentro de un flujo el escenario A crea el estado que B verifica.
  Los escenarios corren en el orden del archivo: escríbelos en el orden del documento, con el estado encadenado en
  variables de la función del flujo.
- Un ayudante propio (como `stringField`) va en tus archivos, recibe el `*Scenario`, llama a `s.Helper()` y falla
  por `s`. Su nombre no puede chocar con uno del arnés: es el mismo paquete.
- Si el `Given` de un flujo depende de datos creados por **otro** flujo, tras el reset no se sostiene: es un hueco
  del diseño, no se siembra a mano.

## Del DSL al cable

Quien escribe estas pruebas no puede mirar el código, así que la forma exacta de la respuesta hay que
**derivarla**, en este orden de precedencia:

1. **`specs/validation-scenarios.md`**: el `Then` literal y las Convenciones de determinación (ausencia vs. nulo,
   orden de las colecciones, escala decimal, colación, formato temporal).
2. **`docs/openapi.yaml`**: el contrato formal de la API. Existe siempre que hay API —si no se pasó `/keel-docs`,
   build lo DERIVA del mismo modelo que el código (`x-keel-derived`), el mismo, byte a byte, que el de los otros
   tres generadores—: rutas, status, cuerpos con sus cotas y cada respuesta con TODOS sus campos, qué puede ser
   null y `additionalProperties: false`. Con él se aserta el cuerpo entero (`AssertJSON`), no campo a campo.
3. **`specs/<capa>.keel.yaml`** con `{{keel:docs}}/wire-contract.md`: la derivación mecánica.
4. Nada más. Lo que estas fuentes no fijan es un `designGap`.

| Qué necesita la prueba | De dónde sale |
|---|---|
| Ruta | `RouteBase` + `endpoints.<op>.path` de `api.keel.yaml` |
| Path / query / cuerpo | cada `{segmento}` es de la ruta; el resto del `input` va en el cuerpo en `POST`/`PUT`/`PATCH` y como query en `GET`/`DELETE` |
| Status de éxito | `endpoints.<op>.successStatus`; si no se declara, 200, salvo `DELETE` (204) y `create*` (201) |
| Cuerpo de error | `{timestamp, status, error, code, message, details, correlationId}`: se afirman el `code` y el status; el resto por presencia y forma, nunca el `message` literal |
| Página | `{items, page, size, totalElements, totalPages}` |
| Instante | ISO-8601 UTC con **tres** decimales y `Z`: `"<instant>"` en `AssertJSON` |
| Decimal | con la escala del diseño: `AssertJSON` lo compara por su texto (`12.50` no casa con `12.5`) |
| Campo sin valor | `null` o ausente según la convención del servicio: decide si la clave va en el JSON esperado |
| `PATCH` | ausente ≠ `null` explícito cuando el diseño lo declara: dos escenarios |
| `Location` | URL **absoluta** (esquema y host de la petición, como los otros tres servidores): se afirma su **final** con `strings.HasSuffix`, nunca la URL exacta, aunque el `Then` escriba solo la ruta |
| `page`/`size` fuera de rango | no son error: `size` < 1 → `defaultSize`, `size` > `maxSize` → `maxSize`, `page` < 0 → 0. Un 400 solo si el escenario lo fija |

## Aserciones: el cuerpo completo o nada

- `AssertJSON` sobre el cuerpo entero: comprueba los campos presentes **y** que no venga ninguno de más. Con
  `"<uuid>"`/`"<instant>"`/`"<any>"` en lo no determinista.
- La escala es parte de la aserción: `AssertJSON` compara los números por su texto, y en una aserción suelta se
  compara el `json.Number` de `got.JSON()` como texto (`n.String() == "12.50"`), nunca convertido a `float64`, que
  da `12.5` aunque el servidor haya perdido la escala.
- Un escenario que no fija qué respuesta gana (una carrera) afirma cada una contra el conjunto de las admitidas, y
  después el estado resultante por la API.
- Un id o una marca de tiempo **nunca** por literal: por forma, y reutilizado dentro del flujo.
- Un test que solo comprueba el status **no vale**.

## Traducir el `Given`

Cláusula por cláusula, cada una con su llamada de siembra **cuyo status se comprueba**: crear la entidad no es
dejarla en el estado que el escenario declara.

| Cláusula del `Given` | No basta con | Hace falta |
|---|---|---|
| `p1 (active)` | crear `p1` (nace en el estado inicial) | la operación que lo transiciona a `active` |
| `c1 con 3 productos` | crear `c1` | crear los tres y comprobar que quedan asociados |
| `p1 sin imágenes` | crear `p1` | nada más, pero decláralo en un comentario |

Lo que el flujo entero necesita antes de su primer escenario va en el `given` de `StartFlow`
(`StartFlow(t, func(s *Scenario) {…})`). Si el `Given` **no se puede materializar por la API**, es `designGap`: no
se siembra por la base. `s.Db(...)` es para **leer** lo que la API no expone (que una escritura llegó al almacén), y
solo excepcionalmente para una precondición que ninguna operación puede fabricar — y entonces se dice en
`assumptions`. Si esa fila lleva una columna sombra `<campo>_normalized` (un campo con `compare`), va con el valor
plegado del campo, nunca con `''`: es la columna que lleva la unicidad.

Al aislar una guarda tardía, las anteriores se satisfacen con datos **válidos**: un cuerpo `{}` muere en otra
guarda, con otro `code`, y el escenario mide lo que no es suyo.

Cada alta lleva su propia clave de idempotencia cuando la operación la declara: un uuid nuevo, escrito como literal
en la prueba, salvo en los escenarios que repiten la anterior a propósito.

## Checklist antes de cerrar

1. Toda ruta usada existe en `api.keel.yaml` y su verbo coincide.
2. Todo `code` de error está copiado **literal** del diseño.
3. Todo campo del cuerpo esperado está en el `output` de la operación; uno que no, es `designGap`.
4. Ningún valor no determinista se compara por literal.
5. Cada escenario con su id exacto delante de los dos puntos.
6. Toda restricción declarada sobre una entrada (`min`, `max`, `minLength`, `maxLength`, `pattern`…) tiene su
   escenario de rechazo con **400** `VALIDATION_ERROR`, aunque el flujo no la nombre.
7. Cada cláusula del `Given` tiene su siembra con su status comprobado.
8. Los decimales se afirman por su texto.
9. Todo archivo con `//go:build integration`, y ningún import del servicio.
10. `bash infra/check-flows.sh` en verde.

## El arnés es del generador

Los archivos de `tests/integration/` con la cabecera de código generado y los scripts de `infra/` los escribe
`keel-go build`. En la fase 1 son de **solo lectura**: sin infraestructura no se puede saber si están rotos, y lo
que falte va a `blockers` con la firma propuesta. En la fase 2, si el árbitro dice `culprit: harness`, se parchea
**al mínimo** en el archivo del arnés que lo tiene, se verifican **todos** los flujos que usan lo tocado y el parche
se registra en `harnessPatches` — es lo que devuelve el defecto al generador. Un defecto fuera de
`tests/integration/` (`infra/`, `go.mod`) no se toca: va a `blockers` y lo corrige el orquestador.

## Lo que se declara en vez de simularse

Un escenario que el diseño no permite ejercitar de forma determinista **no se inventa**: va a `uncovered` con su
motivo. Nada de dobles de prueba ni de `httptest`: lo que se valida es el servidor real contra la infraestructura
levantada.

## Ejecución

```bash
bash infra/check-flows.sh                                                    # caja negra + go vet (fase 1)
go test -tags integration -count=1 -run '^TestProductCreation$' ./tests/integration/   # un flujo (fase 2)
go test -tags integration -count=1 -run '^TestHarnessSmoke$' ./tests/integration/      # el humo del arnés
bash infra/score-scenarios.sh                                                # la suite y la matriz (lo ejecuta el orquestador)
```

`-count=1` no es opcional: sin él, `go test` reutiliza un resultado en caché aunque la base haya cambiado. El arnés
compila y arranca el servidor él mismo; `go test ./...` NO ejecuta los flujos (la restricción los deja fuera a
propósito). Cada fallo deja `build/keel-failures/<FL-id>.json` (escenario, aserción, la última petición y
respuesta, el último sondeo) y un flujo que no arranca, `build/keel-failures/<TestFlujo>-init.json`: sus casos salen
OMITIDOS. La salida del servidor está en `build/keel-scenarios/server.log`.
